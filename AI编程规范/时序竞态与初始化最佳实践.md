# 时序竞态与初始化最佳实践

> **文档定位**：本文件是 PumpGF 在"初始化时序 / 跨对象引用 / 异步加载竞态"领域的强制规范。
> AI 编程助手在编写涉及**对象创建、跨对象引用获取、场景/关卡加载、异步初始化**的代码前**必须**阅读本文件。
> 配套必读：[`开发编程规范.md`](./开发编程规范.md)、[`R3与UniTask使用指南.md`](./R3与UniTask使用指南.md)。

## 0. 问题命名（行业共识）

这类"编辑器正常、打包后报空"的问题，在游戏开发界统称：

| 命名 | 含义 |
|------|------|
| **初始化顺序竞态（Initialization-Order Race Condition）** | 多个对象/系统的初始化顺序未显式约束，依赖对方先就绪的一方在对方就绪前执行 |
| **生命周期依赖竞态（Lifecycle Dependency Race）** | 消费方的生命周期回调（Awake/Start/Update）早于生产方的就绪时机 |
| **"边加载边消费"竞态（Load-While-Consuming Race）** | 异步加载尚未完成，消费方已开始读取其产物，得到 null 或半成品 |

> **Unity 的官方立场**：Unity **不保证**同场景内不同 MonoBehaviour 的 Awake/Start/Update 调用顺序（除非用 `[DefaultExecutionOrder]` 或 Script Execution Order 设置，但二者都是全局静态优先级，无法表达"动态对象 A 生成后 B 才取引用"这种**运行时数据依赖**）。Unity 官方推荐的做法就是：**不要把跨对象的运行时依赖建立在 Awake/Start 的隐式顺序上**，而应通过显式的初始化协议 / 事件 / 异步等待来表达"谁先就绪"。

这正是 PumpGF 引入下列三项机制的根因。

## 1. 框架提供的三道防线

### 防线一：就绪注册表 `GameGlobal.Readiness`（ReadinessRegistry）

把"等待某对象/服务就绪"提升为**一等公民操作**，替代散落的 `WaitUntil(polling)` 与隐式 Awake/Start 依赖。

| API | 用途 |
|-----|------|
| `GameGlobal.Readiness.MarkReady<T>(instance)` | 生产者宣告"我已就绪"，唤醒所有等待者（类型键，一类型一实例） |
| `GameGlobal.Readiness.MarkReady(key, instance)` | 字符串键版本（多实例/动态命名，如 `"Enemy:1234"`） |
| `await GameGlobal.Readiness.WaitUntilReady<T>(ct)` | 消费者安全等待，已就绪则同步完成（无挂起） |
| `GameGlobal.Readiness.TryGet<T>(out var x)` | 同步查询，不阻塞 |
| `GameGlobal.Readiness.IsReady<T>()` / `IsReady(key)` | 布尔查询 |
| `GameGlobal.Readiness.Clear<T>()` / `Clear(key)` | 对象销毁/场景卸载时清除就绪标记 |
| `GameGlobal.Readiness.ClearAll()` | 场景整体切换时清空，防跨场景脏数据 |

**关键特性**：
- 使用 `AttachExternalCancellation`——单个等待者取消**不会**影响其他等待者或源。
- 已就绪时 `WaitUntilReady` **同步返回**，零开销。
- 主线程调用假设。

### 防线二：场景有序初始化 `SceneBootstrapper` + `ISceneInitializable`

把场景内"跨对象初始化"从不可控的 Awake/Start 时序，收敛为**显式、有序、可 await** 的流程。

| 角色 | 职责 |
|------|------|
| `ISceneInitializable` | 实现 `int Priority` + `UniTask InitializeAsync(ct)`，在其中完成**跨对象**装配 |
| `SceneBootstrapper`（MonoBehaviour） | 挂场景根节点，Start 时按 Priority 降序 await 调用所有 `ISceneInitializable`；提供 `WaitUntilInitializedAsync()` / `IsInitialized` |

**关键约定**：
- `[DefaultExecutionOrder(-900)]` 使引导器 Start 早于普通脚本，率先发起初始化。
- Awake/Start **只做自身局部**初始化（字段、同对象组件引用）；**跨对象**依赖一律放 `InitializeAsync`。
- 消费方若不实现 `ISceneInitializable`，可在 Update 订阅前 `await SceneBootstrapper.Current.WaitUntilInitializedAsync()`。
- 提供超时保护（`_maxInitSeconds`，默认 30s），防卡死在 Loading。

### 防线三：两阶段关卡 `IPhasedLevel` + `LevelManager.LoadLevelPhasedAsync`

把关卡加载拆为 **Preload（异步预载）** → **Activate（就绪激活）** 两段，从流程上消除"边加载边消费"窗口。

| 阶段 | 做什么 | 禁止做什么 |
|------|--------|-----------|
| `OnPreloadAsync` | 异步加载场景、实例化对象、加载依赖资源（可带进度→Loading UI） | 绑定 Update、获取其它对象引用、触发依赖就绪的消费逻辑 |
| `OnActivateAsync` | 跨对象引用装配、事件订阅、`Readiness.MarkReady` 宣告就绪 | —— |
| 返回后 | LevelManager 才绑定 Update Tick，关卡正式运转 | —— |

**关键保证**：Activate 在 Preload 完全结束后才执行，因此 Activate 内访问任何 Preload 产物都安全——**彻底消灭"生成 A 与脚本 B 获取 A 引用"的竞态**。

> 旧 `ILevel` 单阶段路径保留兼容，但**新关卡必须用 `IPhasedLevel`**。

## 2. 决策树：我该用哪道防线？

```
你的代码需要"拿到另一个对象/服务的引用"吗？
├─ 否 → 不涉及，正常写
└─ 是 → 那个对象是"场景内同场景的对象"还是"全局/跨场景的服务"？
    │
    ├─ 全局/跨场景服务（如 PlayerController 单例、某 Manager）
    │   → 防线一：ReadinessRegistry
    │     生产方：MarkReady<T>；消费方：await WaitUntilReady<T>(ct)
    │
    ├─ 场景内同场景对象（关卡里一起生成的实体）
    │   → 防线二：ISceneInitializable + SceneBootstrapper
    │     依赖项 Priority 更高，被依赖方在 InitializeAsync 里取引用
    │
    └─ 整个关卡/场景的加载流程（含场景切换）
        → 防线三：IPhasedLevel
          Preload 加载，Activate 装配，Update 最后才绑
```

三道防线可组合使用，例如：两阶段关卡的 `OnActivateAsync` 末尾调用 `GameGlobal.Readiness.MarkReady<BattleLevel>(this)`，让全局系统也能等到关卡就绪。

## 3. 🚫 禁止项（无例外）

### 🚫 禁止在 Awake/Start 里获取**运行时动态生成对象**的引用

```csharp
// 🚫 脚本 B 在 Start 里直接拿 A 的引用
public class B : MonoBehaviour
{
    void Start()
    {
        var a = FindObjectOfType<A>(); // A 可能尚未生成 / 尚未就绪
        a.DoSomething(); // 打包后高频 NullRef
    }
}
```

**原因**：`FindObjectOfType`/`GetComponent` 在对方 Awake 完成但业务状态未就绪时仍可能返回非 null，但"业务就绪"与"对象存在"是两回事。编辑器下因加载快掩盖，打包后暴露。

### 🚫 禁止用 `WaitUntil(() => xxx != null)` 轮询等待就绪

```csharp
// 🚫 协程里轮询，每帧检查，时序不可控
IEnumerator WaitPlayer()
{
    yield return new WaitUntil(() => PlayerInstance != null);
    PlayerInstance.Attack(); // 仍然依赖 PlayerInstance 在哪赋值，时序黑盒
}
```

**替代**：`await GameGlobal.Readiness.WaitUntilReady<PlayerController>(ct);`

### 🚫 禁止在 Preload 阶段消费 / 绑定 Update

```csharp
// 🚫 IPhasedLevel.OnPreloadAsync 里就取引用并启用逻辑
public UniTask OnPreloadAsync(ILevelData data, IProgress<float> progress, CancellationToken ct)
{
    var player = await ResMgr.InstantiateAsync("Player", ...);
    _playerCtrl = player.GetComponent<PlayerController>();
    _playerCtrl.BeginCombat(); // 🚫 Preload 阶段就消费，敌人可能还没生成
}
```

**替代**：Preload 只产出，Activate 才装配 + 启用。

### 🚫 禁止依赖 Unity 的 Script Execution Order 来解决"运行时数据依赖"

Script Execution Order 解决的是"脚本 A 的 Update 永远在 B 之前"这种**静态全局顺序**，无法表达"对象 A 是动态生成的，B 要等 A 生成后才能取引用"。用它来解决运行时数据依赖是误用。

## 4. ✅ 推荐做法

### ✅ 全局服务：生产-消费解耦

```csharp
// 生产者：PlayerController
public class PlayerController : MonoBehaviour
{
    async UniTaskVoid Start()
    {
        // ... 自身初始化 ...
        _hp = maxHp;
        GameGlobal.Readiness.MarkReady<PlayerController>(this); // 宣告就绪
    }
    void OnDestroy() => GameGlobal.Readiness.Clear<PlayerController>();
}

// 消费者：任意脚本、任意时机
async UniTaskVoid OnEnemySpawn(CancellationToken ct)
{
    var player = await GameGlobal.Readiness.WaitUntilReady<PlayerController>(ct);
    player.TakeDamage(10); // 保证就绪，绝不 NullRef
}
```

### ✅ 场景内有序初始化

```csharp
public class EnemySpawner : MonoBehaviour, ISceneInitializable
{
    public int Priority => 800; // 在 PlayerController(900) 之后初始化
    public async UniTask InitializeAsync(CancellationToken ct)
    {
        // 此时 PlayerController 已被 SceneBootstrapper 在更高优先级完成装配
        // （前提：PlayerController 也实现 ISceneInitializable，Priority=900）
        _player = GameGlobal.Readiness.TryGet<PlayerController>(out var p) ? p : null;
        await SpawnInitialWaveAsync(ct);
    }
}
```

### ✅ 两阶段关卡

```csharp
public class BattleLevel : IPhasedLevel
{
    public async UniTask OnPreloadAsync(ILevelData data, IProgress<float> progress, CancellationToken ct)
    {
        // 阶段 1：只产出，不消费
        _scene = await GameGlobal.LevelManager.LoadSceneAsync("Battle", LoadSceneMode.Single, progress, ct);
        _playerObj = await GameGlobal.ResMgr.InstantiateAsync("Player", pos, rot, ct);
        await GameGlobal.ResMgr.PreloadAsync(new[]{ "Enemy/Goblin", "Enemy/Orc" }, progress, ct);
    }

    public async UniTask OnActivateAsync(CancellationToken ct)
    {
        // 阶段 2：Preload 全部就绪后装配
        _player = _playerObj.GetComponent<PlayerController>();
        _player.Init(_data);
        GameGlobal.Readiness.MarkReady<PlayerController>(_player);
        // 关卡就绪后，LevelManager 才绑 Update
    }

    public void OnUpdate(float dt) { /* 关卡逻辑 */ }
    public async UniTask OnExitAsync(CancellationToken ct)
    {
        GameGlobal.Readiness.Clear<PlayerController>();
        await GameGlobal.LevelManager.UnloadSceneAsync(_scene, ct);
    }
}
```

## 5. 初始化优先级参考分级

| 层级 | Priority 区间 | 典型对象 |
|------|--------------|----------|
| 全局服务 | 1000 | GameManager、SaveSystem 接入 |
| 玩家主体 | 900 | PlayerController |
| 敌人/AI | 800 | EnemySpawner、AIDirector |
| UI/表现 | 700 | HUD、BattleUI |
| 杂项/装饰 | 0+ | 特效管理、环境 |

> 数值越大越早；同区间按 SceneBootstrapper 发现顺序（不保证），**有依赖关系的对象必须用不同 Priority 显式区分**。

## 6. 自检清单（AI 生成代码后必查）

- [ ] 是否在 Awake/Start 里获取了**运行时动态生成对象**的引用？是→改用 Readiness / ISceneInitializable。
- [ ] 是否用了 `WaitUntil(() => x != null)` 轮询？是→改用 `Readiness.WaitUntilReady`。
- [ ] 关卡/场景加载是否单阶段混了加载与消费？是→改用 `IPhasedLevel` 两阶段。
- [ ] 跨对象依赖是否用了 `FindObjectOfType` / 全局静态赋值？是→改用 Readiness 或 InitializeAsync 显式传递。
- [ ] Preload 阶段是否绑定了 Update / 触发了消费逻辑？是→移到 Activate。
- [ ] 生产方是否在真正就绪后调用 `MarkReady`？销毁时是否 `Clear`？
- [ ] 有依赖关系的 `ISceneInitializable` 是否用了不同 Priority 显式排序？
