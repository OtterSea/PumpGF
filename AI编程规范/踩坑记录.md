# PumpGF 踩坑记录

本文档收录 PumpGF 框架开发过程中曾经踩过的坑，供 AI/人类开发者参考避免。

**AI 编码时如遇到相同错误，请优先按此清单排查。**

> ℹ️ **背景说明**：本文档中"坑 1 ~ 坑 8"绝大多数是**作者早期误用 Unity 2021 打开框架时踩出来的兼容性坑**。当前 PumpGF 已明确只支持 **Unity 2022.3 LTS**（详见 [`README.md`](../README.md)），这些坑在 Unity 2022 LTS 环境下大多不再复现。保留在这里是作为历史记录，同时防止 AI 生成代码时无意间用回 Unity 2021 的写法。

---

## 1. R3.Subject / R3.Observable ≠ System.IObservable

R3 为了性能，**没有让 `Observable<T>` 继承 `System.IObservable<T>`**。它们是两套 API。

- 编译错误：`error CS0266: Cannot implicitly convert type 'R3.Subject<T>' to 'System.IObservable<T>'`
- ✅ 正确：对外暴露事件流用 `R3.Observable<T>`（`Subject<T>` 可隐式转换为它），而不是 `System.IObservable<T>`。
- ❌ 错误：用 `System.IObservable<T>` 做返回类型或字段类型。

## 2. Unity 2021 缺少 GameObject.destroyCancellationToken

- Unity 2022.2+ 才有 `Component.destroyCancellationToken` / `GameObject.destroyCancellationToken`。
- Unity 2021 编译错误：`error CS1061: 'GameObject' does not contain a definition for 'destroyCancellationToken'`
- ✅ 兼容方案（若必须支持 2021）：改用 UniTask 提供的扩展 `owner.GetCancellationTokenOnDestroy()`（见 [`AsyncTriggerExtensions.cs`](../Vendor/UniTask/Runtime/Triggers/AsyncTriggerExtensions.cs)）。
- ✅ 推荐方案：直接强制 Unity 2022.2+（本框架的做法）。**AI 生成新代码时优先使用 `destroyCancellationToken`。**

## 3. UniTask.DOTween 扩展默认关闭

- `Vendor/UniTask/Runtime/External/DOTween/DOTweenAsyncExtensions.cs` 原始版本包在 `#if UNITASK_DOTWEEN_SUPPORT` 内，宏由 `UniTask.DOTween.asmdef` 通过 `versionDefines` 检测 UPM 包 `com.demigiant.dotween` 是否安装来触发。
- 本框架用源码方式引入 DOTween（`Vendor/Demigiant/`），**不通过 UPM 安装**，所以宏永远不会被定义 → `Tween.ToUniTask()` 找不到 → 各 `.DOFade(...).ToUniTask(ct)` 全部报错。
- ✅ 已修复：改造 [`UniTask.DOTween.asmdef`](../Vendor/UniTask/Runtime/External/DOTween/UniTask.DOTween.asmdef)，直接引用 `DOTween-Scripts`；同时移除 `DOTweenAsyncExtensions.cs` 里的 `#if/#endif` 包裹。

## 4. TMP_Settings.defaultFontAsset 只读

- Unity 版本更新后 `TMP_Settings.defaultFontAsset` 变为只读属性，不能直接赋值。
- ✅ 现改为：切换语言时通过 `LocalizationMgr.OnFontChanged` 事件通知业务层，业务层自行遍历 `TMP_Text` 组件更新字体。

## 5. UnityEngine.Object 与 System.Object 命名歧义

- 在同时 `using UnityEngine;` 和写了 `System.Object`（或 `object` 隐式）的文件里，`Object.Destroy(...)` / `Object.DontDestroyOnLoad(...)` 会产生歧义。
- ✅ 用 `using UObject = UnityEngine.Object;` 别名 + 显式 `UObject.Destroy(...)`。

## 6. Addressables 相关命名空间容易漏

- `Addressables` 类在 `UnityEngine.AddressableAssets`
- `AsyncOperationHandle` 在 `UnityEngine.ResourceManagement.AsyncOperations`
- `SceneInstance` 在 `UnityEngine.ResourceManagement.ResourceProviders`

三者常一起用，缺一个就报 `CS0246` / `CS0103`。

## 7. UniTask 是 struct，不能用 `??=`

- `UniTask` 是值类型，不是引用类型。写 `_initTask ??= InitCoreAsync()` 会报错。
- ✅ 用 `UniTask?` 可空包装 + 手动 `if (_initTask == null)` 判空。

## 8. ResMgr.LoadAssetAsync 泛型约束

- `LoadAssetAsync<T>` 内部走 Addressables，约束 `T : UnityEngine.Object`。
- 如果外层接口（如 `IConfigProvider.LoadConfigAsync<T> where T : class`）比这个宽松，需要在实现里先按 `UnityEngine.Object` 加载再向下转型。

## 9. R3 核心 DLL 的 Editor 平台勾选

R3 的三个核心 DLL 内置在 [`Vendor/R3.Unity/Runtime/Plugins/`](../Vendor/R3.Unity/Runtime/Plugins)：

- `R3.dll`
- `Microsoft.Bcl.AsyncInterfaces.dll`
- `Microsoft.Bcl.TimeProvider.dll`

这三个 DLL 的 `.meta` 文件里必须把 `Editor` 平台设置为 `enabled: 1`。如果被误关闭，会出现类似：

```
UnityFrameProvider.cs(1,10): error CS0234: The type or namespace name 'Collections' does not exist in the namespace 'R3'
```

的编译错误。

- ✅ 修复方法：在 Unity Inspector 里选中三个 DLL，把 `Editor` 平台勾选启用，或者直接编辑对应 `.meta` 文件。

## 10. RuntimeInitializeOnLoadMethod 时机过早导致 MonoBehaviour 不工作

**背景**：[`GameGlobal.cs`](../Runtime/Core/GameGlobal.cs) 使用 `[RuntimeInitializeOnLoadMethod]` 在游戏启动时自动创建 `LifecycleDriver`（MonoBehaviour），用于驱动框架的 Tick 生命周期。

**错误现象**：在 **Editor** 里一切正常，但 **Standalone Build（exe）** 后，`LifecycleDriver.Update()` 从未被 Unity PlayerLoop 调用，导致所有注册到 `LifecycleMgr` 的 Tick 回调（包括输入采样、FSM、Combat 等）全部静默失效。外在表现为：角色完全无法操控，WASD 无响应，但无任何报错日志。

**原因**：原代码使用 `RuntimeInitializeLoadType.AfterAssembliesLoaded`。该时机位于 Unity 启动序列的最早期——此时 **Unity PlayerLoop 尚未初始化**。在这个阶段通过 `new GameObject()` + `AddComponent<MonoBehaviour>()` 创建的对象虽然实例化成功，但 Unity 不会将其纳入 PlayerLoop 的 Update 调度列表。Editor 下不受影响是因为 Editor 的 PlayerLoop 管理方式不同。

**修复方案**：

```csharp
// ❌ 错误 — 太早，PlayerLoop 未就绪
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)]

// ✅ 正确 — PlayerLoop 已就绪，Scene 尚未加载
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
```

**适用场景规则**：
- 需要创建 `GameObject` / `MonoBehaviour` 的初始化 → 至少用 `BeforeSceneLoad`
- 纯静态数据/字典的初始化 → 可用 `AfterAssembliesLoaded`（不涉及 Unity 引擎对象）
- 需要引用场景中已有 GameObject → 用 `AfterSceneLoad`

**发现日期**：2026-07-19

## 11. FSM `.When()` 用"状态自身完成度"做转换条件，而非在 OnUpdate 写 if-else

**背景**：Boss 行为链（召唤→轰炸→吐舌→冲撞→…循环）需要"一个行为播完自动进下一个，且末尾回到首个形成循环"。直觉写法是在子状态机的 `OnUpdate` 里判断"当前行为完了没，完了就 `ChangeState(下一个)`"，这会退化成一坨 if-else 分支，违反 [约束清单铁律 2] 的精神（状态转换逻辑应声明式表达）。

**正确模式**：让每个行为 State 暴露一个**纯只读**的完成度属性，转换条件只读它：

```csharp
// 行为 State 基类：只读完成标志，OnEnter 时复位，行为跑完置 true
public abstract class BossBehaviorState : State
{
    public bool IsCompleted { get; protected set; }
    public override void OnEnter() { IsCompleted = false; /* 启动行为 */ }
}

// 子状态机构建：链式 + 末尾回首（循环），条件只读 IsCompleted（纯查询，无副作用）
builder.State(behaviorA, () => new SummonState(ctx))
       .TransitionTo(behaviorB).When(() => IsCurrentBehaviorCompleted(sm));
// …最后一个行为 .TransitionTo(第一个行为) 形成循环

// 顶层机需要"下钻子状态机取当前 State 的完成度"时：
private bool IsCurrentBehaviorCompleted(StateMachine sub)
    => sub.CurrentState is BossBehaviorState b && b.IsCompleted;
```

**要点**：
- `.When()` 里只有 `is`/属性读取，零副作用、零分配，符合铁律 2。
- "循环"由 `TransitionTo(首状态)` 声明，不在代码里手动 `ChangeState`。
- 顶层机可通过 `StateMachine.CurrentState`（子机可 `as StateMachine` 继续下钻）读取嵌套层级的当前状态，做跨层级条件判断。

**发现日期**：2026-07-26（02 敌人机制 Boss FSM）

## 12. 眩晕/架势条这类"非按伤害累积"的机制，不要硬套 Enemy 基类

**背景**：项目 `Enemy.cs` 的 `ApplyDamage` 内置了"受击即按伤害累积眩晕条"的通用逻辑，普通杂兵适用。但 Boss 的眩晕**只能通过特定交互累积**（弹反舌头、飞石砸中、喘气期挨打），普通命中在非眩晕期是 **0 伤害且不攒眩晕**。若让 `BossActor` 继承 `Enemy`，会强行带上"按伤害攒眩晕"的行为，与需求冲突，且难以干净地关掉。

**正确模式**：Boss 数据层**不继承 Enemy**，只**复用同一批组件契约**（`AttributeSet` / `StunGauge` / `HitMaterialComponent` / `FlashRenderer` / `IDamageable` / `IFactional` / `IDashPierceable`），把"眩晕如何累积"交给独立的 `BossStunReceiver`：

- `BossActor`（数据层）：`ApplyDamage` 只做免伤系数（`DamageTakenMultiplier` 基础=0，眩晕期=1）和掉血/阈值检测，**不碰眩晕**。
- `BossStunReceiver`（累积入口，实现自定义 `IStunReceiver`）：弹反/飞石**显式调** `AddStun(amount, source)`；喘气期订阅 `DamageAppliedEvent` 每击累积。
- `StunGauge.Add` 攒满自发 `StunTriggeredEvent` → FSM 转 Stunned。

**教训**：**"复用基类" ≠ "继承基类"**。当基类内置了与新需求相冲突的默认行为时，优先复用其"组件/契约"而非"继承其类"，用组合把差异点隔离到独立组件，避免继承后再想办法"关掉父类逻辑"的反模式。

**发现日期**：2026-07-26（02 敌人机制 BossActor / BossStunReceiver）

## 13. 跨程序集/跨层反向依赖，用业务层自定义接口做依赖倒置

**背景**：飞石（`Combat` 层通用投射物）命中 Boss（`Enemy` 层）需要给 Boss 累积眩晕。若 `Combat` 直接引用 `Game.Enemy.Boss.BossActor`，会造成 `Combat → Enemy` 的反向依赖，破坏分层（底层通用战斗设施不应知道具体敌人）。

**正确模式**：在**底层**定义窄接口，**上层**实现它，底层只按接口通信：

```csharp
// Combat 层（底层）定义
namespace Game.Combat { public interface IStunReceiver { void AddStun(float amount, GameObject source); } }

// 飞石命中时，只按接口取，不认识具体 Boss 类型
target.GetComponentInParent<IStunReceiver>()?.AddStun(gain, gameObject);

// Enemy 层（上层）实现
public class BossStunReceiver : MonoBehaviour, Game.Combat.IStunReceiver { /* … */ }
```

同理，Boss 的行为 State 需要"召唤小怪 / 发射投射物 / 取玩家位置 / 竞技场边界"等外部依赖时，定义 `IBossContext` 接口由场景编排器（`BossArenaController`）实现，行为 State 只持有 `IBossContext`，不直连场景对象。**依赖倒置让行为逻辑可单测、可复用、不被场景装配绑死。**

**发现日期**：2026-07-26（02 敌人机制 IStunReceiver / IBossContext）

## 14. 慢动作/时停用 `LifecycleMgr.SetChannelTimeScale`，禁用 `Time.timeScale`

**背景**：Boss 终结演出需要"慢动作"。直觉是设 `Time.timeScale = 0.2f`，但这会**全局**影响所有系统（含 UI 动画、音频调度、其他 Channel），且 `Time.timeScale=0` 会让基于 `Time.deltaTime` 的逻辑全部停摆，难以精细控制"只慢战斗、不慢 UI"。

**正确模式**：框架的 `LifecycleMgr` 支持**按 Channel 独立时间缩放**：

```csharp
// 只慢逻辑通道，UI/输入通道不受影响
GameGlobal.LifecycleMgr.SetChannelTimeScale(UpdateChannel.Logic, 0.2f);
// 演出结束恢复
GameGlobal.LifecycleMgr.SetChannelTimeScale(UpdateChannel.Logic, 1f);
```

注册到该 Channel 的 Tick 回调收到的 `dt` 已是缩放后的值，逻辑无需改动。**任何"局部时停/慢放"都应走 Channel 级缩放，而非全局 `Time.timeScale`。**

**发现日期**：2026-07-26（02 敌人机制 BossFSM Finisher）

## 15. AudioMgr 播放前必须先 `LoadConfigAsync`，否则 `Play*` 静默不发声

**背景**：`AudioMgr`（`Runtime/Audio/AudioMgr.cs`）的音效播放（`Play` / `Play3D`）依赖运行时已加载的 `AudioConfigSO`——每个音效 key 对应配置里的一条 `AudioEntry`（含 clip 的 Addressables key、类型、音量、是否 3D 等）。配置不是自动加载的，必须业务侧显式调用一次 `await AudioMgr.LoadConfigAsync(configKey)`。

**错误现象**：代码里 `GameGlobal.AudioMgr.Play("hit_flesh")`（或经 `EffectPlayer.PlaySound` / `PlaySound3D` 间接调用）**没有任何异常、没有崩溃**，只在控制台出一条 `Warning`（大意"未找到 AudioEntry / 配置未加载"），返回 `null` 句柄，然后**完全没有声音**。极易被误判为"音效资源没配好"或"音量为 0"，实际是配置压根没加载。

**原因**：`AudioMgr.Play(key)` 内部先查已加载配置里的 `AudioEntry`，查不到就 `Log.Warning` 后 `return null`，不抛异常也不阻断流程。若全局从未调用过 `LoadConfigAsync`，则任何 key 都查不到 → 所有音效静默失败。

**修复方案**：在战斗/关卡场景启动流程里，与"注册对象池"同处，补一次配置加载（与 `GameFlowController` 里 `RegisterDamagePopupPool` 之类的一次性初始化放在一起）：

```csharp
// 场景启动初始化（一次性），务必 await
await GameGlobal.AudioMgr.LoadConfigAsync(audioConfigKey);
// 之后 Play / Play3D / EffectPlayer.PlaySound* 才会真正发声
```

**排查口诀**：听不到音效但控制台只有 Warning 无 Error → 先确认 `LoadConfigAsync` 调过没，再怀疑 clip/音量/3D SpatialBlend。

**关联**：`EffectPlayer.PlaySound` / `PlaySound3D` 只是对 `AudioMgr.Play` / `Play3D` 的薄封装且**忽略返回句柄**，同样受此前置约束——特效池已注册 + 肉质填了 `hitSoundId`，若漏了 `LoadConfigAsync` 仍然没声音。

**发现日期**：2026-07-27（05 角色3C视效优化 · 技术设计阶段通读代码时识别）

## 16. 对象池 / 特效池「用前必须先 Register」，与音效前置对称

**背景**：`PoolMgr.Get(key)` 与其薄封装 `EffectPlayer.PlayAt(effectId, pos)` 都要求对应的池**已经 `Register` 过**。`EffectPlayer.RegisterEffectPool(effectId, prefab, capacity, maxSize)` 内部就是 `PoolMgr.Register`（且带 `HasPool` 判空，可重复安全调用），但它本身**不会被自动调用**——必须业务侧在启动流程里显式注册每个 effectId 对应的池。

**错误现象**：`EffectPlayer.PlayAt("hit_flesh", pos)` **无异常、无崩溃**——内部 `if (!PoolMgr.HasPool(effectId)) return;` 直接静默返回，特效完全不出现。与坑 15 音效静默一模一样：肉质 SO 填了 `hitEffectId`、prefab 也做好了，但只要漏了注册就永远看不到特效。

**原因**：`EffectPlayer.PlayAt` 设计为「未注册即静默兜底不崩」（这是刻意的降级策略），代价是漏注册时毫无报错线索。

**修复方案**：与坑 15 的 `LoadConfigAsync` 放在同一处启动初始化。推荐**数据驱动**：用一个「特效池清单 SO」（`effectId→prefab→容量` 列表）在 `sceneLoaded` 后遍历注册，照抄 `GameFlowController.RegisterDamagePopupPool` 范式：

```csharp
// 场景启动一次性：遍历清单注册
foreach (var e in poolListSO.entries)
    EffectPlayer.RegisterEffectPool(e.effectId, e.prefab, e.capacity, e.maxSize);
// 缺失/为空 → Log.Warning 降级，不崩
```

**排查口诀**：特效不出现但控制台无 Error → 先查 `PoolMgr.HasPool(effectId)` 是否 true（即注册流程有没有跑到），再怀疑 prefab/粒子时长/位置。**「特效池注册」与「AudioConfig 加载」是打击反馈的两个对称隐藏前置，务必同处配齐。**

**发现日期**：2026-07-27（05 角色3C视效优化 · 缺口1 实现）

## 17. 扩展 `readonly struct` 事件 / 命中数据时，用「新增字段 + 保留旧构造重载」缩小改动面

**背景**：项目里事件（`DamageAppliedEvent` 等）与命中数据（`HitInfo`）都是 `readonly struct`（零 GC 设计）。给它们**新增字段**（如补采 `RaycastHit.normal`、加蓄力标志）时，若直接改唯一构造函数的签名，会连锁触发**所有 `new XxxEvent(...)` 调用点**编译失败——命中数据的构造点可能散落在拳头/近战/投射物多个来源，事件的构造点也可能不止一处。

**最佳实践**：
1. 给 struct **追加字段**（放在末尾，不动原有字段顺序）；
2. **新增一个全参构造**（含新字段）；
3. **保留原签名的旧构造作为重载**，用 `: this(..., 兜底值)` 转发到全参构造（如法线兜底 `-hitDirection`、布尔标志兜底 `false`）。

这样：只有真正能提供新数据的主链路（如拳头 `ScanHits` 能拿到 `RaycastHit.normal`）改用全参构造；其余没有该数据的来源（近战/投射物无 RaycastHit）**一行都不用改**，靠旧构造的兜底值自动填充。订阅方因是 `readonly` 只读字段，加字段天然不受影响。

```csharp
public readonly struct HitInfo
{
    // ...原字段... + 新增：
    public readonly Vector3 HitNormal;
    public readonly bool IsChargeHit;

    // 全参构造（新来源用）
    public HitInfo(..., Vector3 hitNormal, bool isChargeHit) { ... }

    // 旧构造重载（老来源零改动，兜底转发）
    public HitInfo(..., Vector3 hitDirection)
        : this(..., hitDirection, -hitDirection, false) { }
}
```

**收益**：把一次"看似要改 4~5 个调用点"的结构扩展，压缩成"只改 1 个主链路 + 加两个构造"，回归风险大幅降低，也契合宪法「业务层最小侵入」。**注意**：旧构造不要删除（它是兼容层），并加注释说明兜底语义，避免后人误以为冗余而清理。

**发现日期**：2026-07-27（05 角色3C视效优化 · 缺口3 命中法线采集）

## 18. `using System;` 与 `UnityEngine.Object` 歧义（CS0104），用全限定名规避

**背景**：`Combat/Fist.cs` 需要给类新增 `public event Action<Fist> Returned;`，直觉是在文件头加 `using System;` 拿 `Action`。但该文件里 `_hitTargets` 字段用的是**未限定的 `List<Object>`**（依赖 `using UnityEngine;` 解析到 `UnityEngine.Object`）。

**错误现象**：加了 `using System;` 后 `Object` 变成二义性标识符：`error CS0104: 'Object' is an ambiguous reference between 'System.Object' and 'UnityEngine.Object'`，且报错点不在新代码、而在**原有的 `List<Object>` 字段处**——改一行引入一个新的全局编译错误。

**原因**：`using System;` 把 `System.Object` 也带入无前缀查找空间，与已有的 `UnityEngine.Object` 冲突；未限定使用 `Object` 的既有代码全部中招。与坑 5 同源，但坑 5 是"两个命名空间都要用、需要别名"，本次是"只想用 `Action`，不必引入整个 `System`"。

**修复方案**：**不引入 `using System;`，只对需要的委托用全限定名**：

```csharp
// ❌ 加 using System; → 既有 List<Object> 全部 CS0104
// ✅ 全限定，文件头保持零新增 using
public event System.Action<Fist> Returned;
```

**要点**：
- 只缺一个 `System` 类型时，用全限定名 `System.Action<T>` / `System.Func<T>` 比 `using System;` 更安全，避免污染整个文件的未限定查找空间。
- 若文件里已有未限定的 `Object` / `List<Object>` 依赖，`using System;` 前先 grep 一遍 `\bObject\b` 确认没有裸用。
- 与坑 5 的区别：坑 5 场景（两命名空间都要用）用 `using UObject = UnityEngine.Object;` 别名；本场景（只想借 `System` 一个类型）用全限定名即可。

**发现日期**：2026-08-05（10 表现层优化2 · T1 Fist.Returned 事件）

## 19. 删除/改名 SO 字段前，必须先 grep 全部调用点

**背景**：模块 B 把 `HitEffectPoolListSO.Entry` 的 `prefab` 字段删除、改为 `assetKey`（Addressable 字符串）。改造了 SO 定义后以为改动完成，实际遗留一个编译错误。

**错误现象**：`GameFlowController.cs` 里既有注册代码仍在 `foreach (var e in poolListSO.entries)` 中访问 `e.prefab`（场景启动注册特效池），`error CS1061: 'Entry' does not contain a definition for 'prefab'`，且**不在本次改造文件里**，静态审计前不会被发现。

**原因**：只改了"定义处"（SO 类），没先搜"使用处"（调用点）。删除字段这类结构性改动，遗留调用点必然编译失败，且报错文件与改动文件分离，排查成本更高。

**修复方案**：**动手前先 grep 旧字段名**（`git grep "\.prefab"` / 搜索 `entry.prefab`、`\.prefab\b`），列出全部使用处，连同定义一起改。本需求的具体修复落在 T3（`GameFlowController` L340/L343 改为 `assetKey` 走新异步池注册）。

**要点**：`prefab` 这类宽泛字段名在项目里可能被多处使用，不要靠"我记得只有一处"判断——`read_lints` 只报当前打开文件的诊断，全仓编译错误要靠全局 grep + 静态审计兜底。

**发现日期**：2026-08-05（10 表现层优化2 · T2 改造后 T3 静态核对时发现）

## 20. 新文件引用工具静态类（`Log` 等）前，先核实其命名空间

**背景**：新建 `Feedback/EffectHandle.cs`（`namespace Game.Feedback`）时直接写 `Log.Warning(...)`。`Log` 类是 PumpGF 框架的通用日志工具，实际位于 **`namespace PumpGF`**（`Packages/PumpGF/Runtime/` 下），不在 `Game.*` 业务命名空间里。

**错误现象**：编译期 `error CS0103: The name 'Log' does not exist in the current context`（或 `CS0246`），文件头只有 `using UnityEngine;`，没有 `using PumpGF;`。若在开发环境未全量编译，会延迟到出包/重开编辑器才暴露。

**原因**：凭"`Log` 是全局类"的直觉直接调用，未核实其真实命名空间。Unity 项目里日志、资源、调度等通用设施几乎都在 `PumpGF` 命名空间，业务层文件必须显式 `using PumpGF;`。

**修复方案**：写新文件引用任何非本命名空间的类型前，先 `search_content` 查 `class Log` / `class ResMgr` 等定义的命名空间，确认后在文件头补 `using PumpGF;`。**口诀：新文件的 using 清单不要凭记忆，先查再写。**

**发现日期**：2026-08-05（10 表现层优化2 · T3 EffectHandle.cs 创建后静态核对时发现）

## 附录：其他引擎的已知不兼容项（非官方支持）

以下内容并非踩坑，而是**在非官方支持的引擎版本上确定不能正常工作**的技术记录，供有兴趣做迁移的高级用户参考。

### 团结引擎 Tuanjie 1.9.x

- 团结引擎会把 `Microsoft.Bcl.AsyncInterfaces`、`Microsoft.Bcl.TimeProvider` 等 BCL 程序集视为**引擎内置模块**，**不允许 `Plugins/` 目录再加载同名 DLL**
- 框架内置在 [`Vendor/R3.Unity/Runtime/Plugins/`](../Vendor/R3.Unity/Runtime/Plugins) 里的三个 R3 相关 DLL 会引发加载冲突，导致团结引擎项目无法正常打开
- R3 官方对此类场景建议使用 [NuGetForUnity](https://github.com/GlitchEnzo/NuGetForUnity) 从 NuGet 源安装 R3
- 如果确认要在团结引擎里使用 PumpGF，具体迁移步骤请参考 [`README.md` 附录](../README.md) 相应章节
- **UIParticle 排查结论（2026-08-05，嵌入时静态排查，未经真机验证）**：`Vendor/UIParticle/Runtime/Coffee.UIParticle.R.dll` 是上游自带的托管裁剪标记程序集（netstandard2.0，仅含程序集级 `AlwaysLinkAssembly` 属性，不含任何类型），程序集名唯一，**不构成 R3 式同名 DLL 冲突**；若团结引擎仍对其报错，可直接删除该 DLL，仅影响 IL2CPP 裁剪标记行为，不影响功能。源码内版本宏（`UNITY_2022_3_OR_NEWER` → `PS_BAKE_API_V2` 等）按 Unity 2022.3 基底正常命中。

### Unity 2021 及更早

- 缺少 `GameObject.destroyCancellationToken`（见坑 2）
- 缺少 `Dictionary.Remove(key, out value)` 等 API
- 不支持 C# 9 的 target-typed new、record 等语法
- 会产生近 40 处编译错误，**不建议尝试**
