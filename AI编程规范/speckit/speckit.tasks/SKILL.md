# SpecKit: Tasks — 任务拆解

## 用途

将开发计划拆解为具体的、可按步骤执行的开发任务。每个任务是独立工作单元，包含足够上下文供 implement 阶段独立理解和执行。产物：`.specify/<主题>/4.tasks.md`。

## 前置条件

- `.specify/<主题>/3.plan.md` 已存在

## 工作流

### Step 1: 读取上下文

- 读取 plan 文件
- 回顾 spec 确保任务覆盖所有需求点
- 用 Glob/Grep 检查项目现有代码，避免任务冲突

### Step 2: 按原则拆解

- **原子性** — 每个任务可独立完成
- **顺序性** — 明确依赖和执行顺序
- **可验证性** — 每个任务有明确验证标准
- **渐进性** — 从基础框架到核心逻辑到细节完善
- **上下文完整** — 任务包含足够信息可独立理解

### Step 3: 分阶段组织

按以下通用阶段组织（具体阶段根据项目调整）：

- **Phase 0: 准备工作** — 目录结构、依赖确认
- **Phase 1: 数据层与接口定义** — 数据模型、接口、枚举/常量
- **Phase 2: 核心模块实现** — 主体逻辑、业务规则
- **Phase 3: 集成层** — 事件注册/解注、模块对接
- **Phase 4: UI 层**（如涉及） — 界面实现、交互绑定
- **Phase 5: 联调与收尾** — 模块注册、异常处理、优化

### Step 4: 生成任务文档

每个任务包含：
- 状态标记（待开始/进行中/已完成/已跳过/有问题）
- 描述、操作步骤、涉及文件、验证标准、依赖关系
- 任务编号：`阶段号.序号`（如 Task 2.3）
- 末尾附任务依赖图和执行检查清单

### 任务状态标记

| 标记 | 含义 |
|------|------|
| ⬜ | 待开始 |
| 🔄 | 进行中 |
| ✅ | 已完成 |
| ❌ | 已跳过 |
| ⚠️ | 有问题 |

## 产物格式

- 路径：`.specify/<主题>/<N>.tasks.md`
- 序号：按主题目录内执行步骤编号
- 涉及文件路径必须精确到实际路径

## 约束

- 不生成业务代码
- 不引用不存在的文件/模块
- 不整读大文件

## 下一步

> 任务清单就绪后：
> - 强烈推荐：执行 `/speckit.analyze` 做跨产物一致性审计
> - 任务极少时可跳过，直接 `/speckit.implement`
